# 02 方案设计

## 架构

```
CLI --requests <ID>
  └─ cli.py 构建任务输入（方案目录/费用表/已有方案/故障注入/续跑历史步骤）
      └─ agent.py  ReAct 循环（步数/工具调用/协议错误上限）
          ├─ gateway.py  真实 LLM（OpenAI 兼容） 或 离线 Mock 决策器（同一 request+trace 接口）
          ├─ tools.py    search_materials / estimate_cost / generate_script / save_plan
          │              + 费用引擎（按 tool_costs.json 计价）
          │              + 步骤状态流水 ctx["steps"]（成功/失败均落账）
          └─ 报告构建器（以工具真值与步骤流水为准；声明核对）
```

## 调用流程与动态决策

每一轮：模型看到「任务 + 候选方案 + 已有步骤 + Trace」→ 输出一个 JSON 动作 → 协议校验 →
执行工具 → 回填观察 → 模型决定下一步或结束。关键决策由工具返回内容触发：

| 工具结果 | 模型下一步 |
|---|---|
| 预算/截止时间缺失（estimate_cost 直接返回 error） | 检索一次素材后立即结束，报告缺失项 |
| estimate_cost 返回超预算（如 12 > 10） | 降级改选下一个候选方案（8），再次估算 |
| 全部候选都不可行 | 结束并报告最低可行成本与缺口（超预算/超时数值） |
| generate_script 失败 | 原地重试一次；仍失败则停止，保留已成功步骤 |
| save_plan 失败 | 原地重试一次；仍失败则停止并如实报未完成（续跑可接上） |
| save_plan 返回 duplicate | 如实报告已有方案，不重复创建 |

两条典型执行路径：
- 参考实例（Q2-01）：`estimate(AP-A:12,超预算) → estimate(AP-B:8,可行) → generate_script → save_plan`（重规划路径）
- 失败续跑（Q2-08→Q2-09）：第一段 `estimate×2 → script → save(失败) → save(重试失败) → stop`；
  第二段 `resumed(跳过估过且成功的步骤) → save(成功)`（断点续跑路径）

## 步骤状态与依赖

- 每次工具调用（含失败）写入 `ctx["steps"]`，报告逐条展示；失败状态明确标注「结果未被记为成功」。
- 依赖校验在工具内完成：`generate_script` 要求同方案存在 `feasible=true` 的估算；
  `save_plan` 要求估算通过 + 脚本成功，并在落库前以最新估算复检预算/时间。
- 续跑：请求可携带 `prior_steps`；循环遇到与历史成功步骤完全相同的动作时直接跳过（记为 resumed），
  只执行未成功的步骤。CLI 用 `--requests Q2-08,Q2-09` 演示两段流。

## 技术取舍

- **原生 Python + JSON 动作协议**：框架名称不加分；原生实现让状态机、依赖校验与续跑逻辑透明可测。
- **费用引擎独立于模型**：所有金额/工期由 `tool_costs.json` 计算，模型只负责选择方案与工序，
  报告中的费用合计一律取自工具返回值，杜绝模型口算误差。
- **Mock 决策器与真实模型共用循环**：Mock 是确定性决策器（基于任务字段、历史步骤与工具观察），
  保证离线可评审；真实模式仅替换决策来源。
- **防虚报**：报告只认工具真值与步骤流水；另对模型总结做声明核对（保存成功/任务完成/预算内）。
- **重复执行与续跑**：`save_plan` 以请求 ID 幂等；续跑以「工具+参数」内容哈希识别已成功步骤。
